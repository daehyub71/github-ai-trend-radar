# SPEC.md — github-ai-trend-radar

> **상태: v0.7.3** (2026-11-14). 확정 결정은 §3(R1~R8)과 §9(D1~D24)에 있다. 열린 결정은 없다(F11 그림 시안은 2026-11-14 합의).
> 문서 간 불일치가 생기면 이 문서가 기준이다.

---

## 1. 프로젝트 목표

**깃허브 AI 저장소의 주간 트렌드를 스타 하나가 아니라 여러 신호로 읽는다.**
스타(관심)에 포크(직접 고쳐 쓰려는 수요), 기여·PR·이슈 활동(커뮤니티와 관리), 패키지 다운로드·의존 수(실제 사용),
커뮤니티 언급(외부 화제)을 더해 신호별 순위와 **종합 트렌드 지수**를 만든다. 결과는 웹 사이트와 블로그 초안·Notion으로 낸다.

이 프로젝트가 돕는 판단은 세 가지다.

1. 이번 주 정말로 **쓰이고 만들어지는** AI 저장소는 무엇인가 (관심만 큰 저장소와 구분)
2. 어떤 저장소가 **어떤 신호로** 뜨고 있는가 (관심형·사용형·기여형의 차이)
3. 이번 주 블로그·영상에서 다룰 저장소는 무엇인가

### 1-1. 푸는 문제

- 스타만 보면 화제성 큰 데모·목록 저장소가 위로 오고, 실제로 많이 쓰이는 라이브러리·도구가 묻힌다.
- 스타는 가짜 스타·하루 몰림에 흔들린다. 다른 신호와 함께 보면 이상치를 가려낼 근거가 생긴다.
- 여러 지표를 사람이 매주 모으면 기준이 흔들린다. 코드가 같은 기준으로 계산해야 한다.

### 1-2. 다른 프로젝트와의 경계

| 프로젝트 | 맡는 일 | 이 프로젝트와의 관계 |
|---|---|---|
| `github-ai-star-trend` | 깃허브 스타 기반 주간 순위·카드·브리핑·블로그 (운영 중) | **그대로 운영한다.** 이 프로젝트는 그 공개 데이터(AI 판정·카테고리·주간 스타 증가)를 **입력으로 읽고**, 스타 수집·AI 판정을 다시 하지 않는다 (R2) |
| `ai-trend-batch` | 깃허브 밖 신호로 보는 AI 도구·모델 주간 동향 | 겹치지 않는다. 그쪽은 저장소 순위를 만들지 않는다 |

## 2. 사용자와 사용 방식

- 사용자 1명(운영자 겸 블로그 작성자). 매주 사이트로 순위를 보고, 블로그 초안을 Notion에서 검토해 직접 게시한다.

## 4. 신호 정의

모든 신호는 **주(일요일 시작, UTC) 단위**로 계산한다. star-trend의 주 경계와 같게 맞춘다.

| ID | 신호 | 주간 값 | 출처 | 비고 |
|---|---|---|---|---|
| S1 | 관심 | 스타 증가 | star-trend `data/stars/` | 입력. 다시 수집하지 않는다 |
| S2 | 개조 수요 | 포크 증가 | GitHub 저장소 메타(`forks_count`) 주간 차이. **소급하지 않는다**(D10) | 템플릿·튜토리얼 저장소는 포크가 부풀려진다 — 표시만 하고 자동 제외하지 않는다 |
| S3 | 기여·관리 | 머지된 PR 수 · PR 작성자 수(고유) · 닫힌 이슈 수 | GitHub Search API(기간별 개수) | 봇 계정(`[bot]`)은 뺀다. 세 값을 각각 백분위로 바꾼 뒤 1:1:1 평균한 것이 S3 값이다(D5) |
| S4 | 실제 사용 | 패키지 다운로드 증가 · 의존 패키지 수 | 패키지 연결: 저장소 이름 조회 + 저장소의 `pyproject.toml`·`setup.py`·`package.json` 이름(D11), 레지스트리의 저장소 URL 이 일치할 때만. 다운로드: pypistats · npm downloads API. 의존 수: ecosyste.ms | 패키지가 없는 저장소는 이 신호가 **없음**(0이 아니다). 의존 수는 이력이 없어 지금부터 쌓는다 |
| S5 | 외부 화제 | 언급 글 수 · 점수 합 | Hacker News(Algolia) · GeekNews | 저장소 URL이나 정확한 이름이 들어간 글만 센다 |

### 4-1. 종합 트렌드 지수 (D1)

1. 신호마다 주간 값을 후보 저장소 안에서 순위 백분위(0~100)로 바꾼다. 큰 저장소가 모든 신호를 압도하지 않도록 값은 로그를 취한 뒤 비교한다.
2. 지수 = 신호별 백분위의 가중 평균. **값이 없는 신호(예: 패키지 없음)는 빼고 남은 가중치로 다시 나눈다.** 빠진 신호는 화면과 글에 표시한다.
3. 저장소마다 신호별 기여분(가중치 × 백분위)을 막대로 보여 준다.
4. 가중치는 `config`에 두고 바꾸면 버전을 올린다. 지난 지수는 그때의 가중치로 남긴다.

**가중치 v1 (D1, 사용·기여 쪽에 더):**

| S1 스타 | S2 포크 | S3 기여 | S4 사용 | S5 언급 |
|---|---|---|---|---|
| 15 | 15 | 25 | 30 | 15 |

- 관심(스타)보다 실제로 쓰이고 관리되는지를 더 본다는 이 프로젝트의 목적을 가중치에 담는다.
- 12주 소급 뒤 신호끼리의 겹침(상관)과 결측률을 실측해 `docs/MEASURE.md`에 남긴다. 한 신호가 결측이 너무 많거나 다른 신호와 거의 같은 값을 내면 v2를 제안하고 사용자와 정한다.

## 5. 기능 요구사항

### F1. 주간 실행

- 매주 1회 무인 실행(GitHub Actions cron). **월요일 09:00 UTC(18:00 KST) 고정 시각**에 돈다(D6). star-trend 월요일 실행은 실측상 04:50 UTC쯤 시작해 06:30 UTC쯤 끝난다(11-02·11-09).
- 시작할 때 star-trend 공개 데이터가 그 주 것으로 갱신됐는지 확인한다. 아직이면 30분 간격으로 최대 4번 다시 확인하고, 그래도 없으면 실행을 멈추고 상태를 남긴다. 두 저장소는 서로를 호출하지 않는다.
- 실행 순서: 입력 읽기 → 후보 선정 → 신호 수집 → 정규화·지수 → 저장 → 사이트 데이터 → 블로그 초안 → Notion.
- 소스마다 상태(`ok`·`partial`·`failed`)를 남긴다. 한 신호가 실패해도 나머지로 지수를 내고, 빠진 신호를 표시한다.

### F2. 후보 선정

- star-trend가 AI로 판정한 저장소 중, 그 주 스타 증가 순위 후보에 들었거나 최근 12주 안에 후보였던 저장소를 후보로 삼는다.
- 후보 수 상한은 **200개**다(D2). 그 주 스타 증가 상위 200에, 지난주 종합 TOP 10 가운데 빠진 저장소를 더한다(지난주와 비교하기 위해서). 상한은 `config`에 둔다.

### F3. 신호 수집

- S2~S5를 후보마다 수집한다. GitHub 호출은 토큰 한도(시간당 5,000회) 안에서 나눠 보내고, 429·5xx는 재시도한다.
- 응답 형식이 바뀌면 조용히 0으로 넘어가지 않고 `partial`로 기록한다.

### F4. 정규화와 지수

- §4-1의 방식으로 신호별 백분위와 종합 지수를 계산한다. 같은 입력이면 같은 결과가 나와야 한다.

### F5. 12주 소급 (R6)

| 신호 | 소급 방법 | 가능 범위 |
|---|---|---|
| S1 스타 | star-trend 공개 데이터 | 52주 (이미 있음) |
| S2 포크 | **소급하지 않는다**(D10) | 소급 구간은 결측 — 지수에서 빼고 가중치를 다시 나눈다. 포크 목록은 1쪽 2.3초에 큰 저장소는 12주 전까지 닿지 못한다(MEASURE §1) |
| S3 PR·이슈 | Search API로 주별 기간 개수 | 12주 가능 |
| S4 다운로드 | pypistats(약 180일 일별) · npm range API | 12주 가능. **의존 수는 소급 불가** — 지금부터 쌓는다 |
| S5 언급 | HN Algolia 기간 검색 · GeekNews `/past?day=` 날짜별 목록(D12, 요청 간격 2초) | 12주 가능(GeekNews 1년 전까지 확인) |

- 소급 결과와 주간 수집 결과는 같은 형식으로 저장하고, 소급으로 만든 값임을 표시한다.

### F6. 웹 사이트 (R7)

- 이번 주 종합 TOP 10과 신호별 순위, 저장소별 신호 막대와 4·12주 추이를 보여 준다. 화면 구성은 DESIGN 시안 합의 뒤에 정한다.
- 저장소 화면에 저장소 해설(F10)과 코드 관찰을 보여 준다. 이번 주 TOP 10 표에는 해설의 "이번 주 왜 올랐나" 한 줄을 붙인다(D16).

### F7. 블로그 초안·Notion (R7)

- **별도 연재「깃허브 AI 트렌드 레이더」로 1회부터 시작한다**(D3). star-trend 연재는 그대로 둔다. 레이더가 안정되면 합칠지 다시 정한다.
- 형식은 사용자 견본(star-trend `docs/ref/blog-sample.md`)의 틀(흐름 → TOP 10 → 저장소별 소개)을 따르되 종합 지수 기준으로 쓴다. 저장소마다 "어떤 신호로 떴는지"를 숫자로 보여 준다.
- Notion에는 상태가 "초안"인 페이지만 만들고 고친다. 자동 게시는 하지 않는다.

### F8. 게이트

- LLM 글의 숫자는 신호 값·순위·지수에 있는 것만, 링크는 수집한 출처에 있는 것만 허용한다. 투자 권유·단정 표현을 막는다.
- 저장소 해설(F10)은 근거 번호(E1…)로만 출처를 단다. 근거 번호가 없는 항목은 뺀다.

### F9. 관점 글 — 이번 주 소재 후보 (D9)

매주 TOP 10 글(F7)과 **별도로 관점 글 초안을 하나 더** 만든다. 신호가 여럿이라 스타 순위만으로는 보이지 않는 저장소를 유형별로 골라, 블로그·영상 소재로 쓴다. 이 문서가 돕는 판단 3("이번 주 블로그·영상에서 다룰 저장소")에 맞는 기능이다.

| 유형 | 고르는 규칙 (코드, 초기값) | 글의 각도 |
|---|---|---|
| A. 조용한 강자 | 스타 백분위 < 50 이고 사용·기여(S3·S4, S4가 없으면 S2·S3) 평균 백분위 ≥ 80 | 화제는 적지만 실제로 쓰이고 관리되는 도구 |
| B. 반짝 관심 | 스타 또는 언급 백분위 ≥ 90 이고 포크·기여·사용 평균 백분위 ≤ 30 | 관심은 큰데 사용·기여 신호는 아직 보이지 않는 저장소 |
| C. 꾸준한 상승 | 종합 지수가 4주 연속 올랐다 | 한 주 반짝이 아니라 자리 잡는 중 |
| D. 신호 전환 | 기여분 막대에서 관심(S1+S5) 비중이 4주 전보다 내려가고 사용·기여(S3+S4) 비중이 20%p 이상 올랐다. **두 주에 값이 있는 신호가 같을 때만**(2026-11-14 추가 — 신호가 새로 채워진 것을 전환으로 잡지 않게, MEASURE §3-5) | 데모에서 실제 도구로 넘어가는 순간 |

- 유형마다 **최대 5개**. 규칙과 거리가 먼 순(조건을 넉넉히 넘는 순)으로 고른다. 조건을 만족하는 저장소가 적으면 적은 대로 내고, 억지로 채우지 않는다.
- 한 저장소는 한 유형에만 넣는다. 겹치면 D → C → A → B 순으로 앞 유형에 넣는다.
- C·D는 4주 이력이 필요하다. 이력이 모자라면 그 유형은 "이력 부족"으로 비워 둔다(12주 소급으로 첫 주부터 채워지는 것이 목표).
- 임계값은 `config`에 두고, M2 소급 실측(유형별 해당 수)으로 한 번 조정한 뒤 고정한다. 바꾸면 버전을 올린다.
- 저장소마다 **고른 근거 숫자**(해당 신호의 백분위·지수 추이)를 코드가 붙이고, LLM은 그 저장소가 무엇이고 왜 이 유형으로 볼 만한지만 쓴다.
- B 유형 글은 판단을 내리지 않는다. "거품"·"가짜" 같은 단정은 게이트가 막고, "사용 신호는 아직 보이지 않는다"처럼 관측만 쓴다.
- 산출물: 비공개 저장소 `weeks/<주>/blog/angles.md`와 Notion 레이더 DB의 별도 페이지(속성 "글 종류" = 관점). 상태가 "초안"인 페이지만 고친다.
- 글 틀: 도입(이번 주 신호 지형 한 문단) → 유형 A~D 절(유형 설명 한 문단 + 저장소별 무엇인가·왜 이 유형인가·근거 숫자 표) → 주의할 점(백분위는 후보 200 안에서의 상대값, AI 판정 기준 등) → 한 장 요약. 그림 자리는 F7과 같은 방식.

### F10. 저장소 해설 — 무엇이고 왜 올랐나 (D13~D16, 2026-11-14 추가)

star-trend 카드는 스타 상위 저장소에만 있어서, 사용·기여로 오른 저장소에는 설명이 없다(예: 11-01 주 종합 6위 `remotion-dev/remotion` — 스타 순위 70위, 주간 다운로드 350만). 레이더 저장소 화면에 **신호 관점의 해설**을 붙인다. 사용자 요청: 3줄 요약, 이번 주 동향, 무엇이고 어떤 역할인지, HN 등에서 어떻게·왜 화제가 됐는지, 포크·다운로드·언급에서 볼 인사이트.

**F10-1. 코드 관찰 — 모든 저장소, LLM 0**

숫자만으로 낼 수 있는 관찰 문장이다. 데이터가 있을 때만 낸다. 임계값·문구는 `config`에 두고 버전을 붙인다(관찰 규칙 v1).

| ID | 관찰 | 계산 |
|---|---|---|
| I1 | 사용 대비 관심 | 주간 다운로드 ÷ 스타 증가 — 패키지가 있는 후보 안 순위 |
| I2 | 다운로드 추세 | 이번 주 ÷ 지난 4주 평균, 12주 첫 주 대비 배수 |
| I3 | 포크 비율 | 포크 증가 ÷ 스타 증가 — 후보 안 백분위. 포크 증가가 없으면 "다음 스냅샷부터" |
| I4 | 기여 폭 | PR 작성자 수 — 이번 주와 4주 전·12주 첫 주 |
| I5 | 언급의 쏠림 | 이번 주 HN·GeekNews 글 수·점수. 글 하나가 점수의 80% 이상이면 "글 하나가 언급 신호를 만들었다", 12주 점수 합이 10 미만이면 "화제보다 사용으로 오른 저장소"(사용 신호가 있을 때) |
| I6 | 의존 | 의존 패키지 수(ecosyste.ms) |
| I7 | 순위 이동 | 종합 순위 지난주 → 이번 주, 12주 최고·최저 |

- 관찰은 공개 데이터 `data/site/repo/<id>.json`에 넣는다(숫자에서 나온 문장이라 공개해도 된다).

**F10-2. AI 해설 — 그 주 TOP 10 + 관점 노트 저장소 (D14)**

- 대상: 그 주 종합 TOP 10과 관점 노트 A~D에 나온 저장소, 겹침을 빼면 주 20~25개.
- 근거 수집(코드, LLM 0, D15):
  - README(6,000자까지), 그 주까지의 릴리스 최근 5개
  - HN 글(12주 — 제목·점수·댓글 수·날짜)과 이번 주 글의 큰 댓글 타래 5개의 첫 댓글(600자까지)
  - GeekNews 글 제목·점수
  - **웹 검색**: Tavily 기본 검색 3회, 발행일 요청 — star-trend 방식. Reddit·X는 링크와 검색 스니펫만 쓰고 본문은 읽지 않는다.
  - 그 주 끝 날 뒤에 발행된 근거는 뺀다. 근거마다 번호(E1…)를 붙인다.
- 해설 구성 — 저장소 하나에 한 번 호출(Sonnet 5.5, JSON 스키마):
  1. **3줄 요약** — 무엇인지 / 이번 주 왜 올랐나(어떤 신호가 지수를 만들었나) / 무엇을 볼까
  2. **이번 주 동향** — 코드 표(신호별 이번 주·지난주·지난 4주 평균, 순위·지수 변화, 이번 주 릴리스) + 해설 항목 2~4개
  3. **무엇인가·어떤 역할** — 해결하는 문제, 구조, 쓰는 사람, 대안과 비교한 자리
  4. **어디서 어떻게 화제가 됐나** — 코드 목록(HN·GeekNews 글) + 해설: 계기, 반응의 요지, 화제의 성격(소개·호평·논란·질문). 언급이 없으면 없다고 쓴다
  5. **신호 인사이트** — F10-1 관찰 + 지켜볼 점 2~3개(포크·다운로드·언급에서 무엇을 볼지)
  6. **근거 목록** — 제목(120자까지)·사이트·날짜
- 화제의 성격 "논란"·"호평"은 그 주 글의 댓글 합이 10개 이상일 때만 붙인다. 아니면 코드가 "소개"로 바꾼다(D17).
- 해설 항목마다 근거 번호와 **확인/추정**을 붙인다(확인 = 근거가 직접 말함, 추정 = 해석). 숫자는 facts에 있는 것만 쓴다(F8). 근거 번호가 없는 항목과 근거 목록에 없는 링크는 게이트가 뺀다.
- 매주 대상 저장소마다 새로 쓴다. 지난 해설은 남긴다. 저장소 화면은 가장 최근 해설과 그 기준 주를 보여 주고, 대상이 아닌 주에는 "마지막 해설: <주>"로 안내한다.
- star-trend에 같은 저장소 카드가 있으면 링크만 단다(내용은 가져오지 않는다).
- 보관(D13):
  - 비공개 저장소 `cards/<repo_id>.json`(최신), `weeks/<주>/cards/`(주별), `site-private/`(사이트용 사본).
  - 사이트는 빌드 때 읽기 전용 토큰으로 `site-private/`만 받는다.
  - 프로덕션 빌드에 토큰이 없으면 빌드를 실패시킨다. 해설이 말없이 빠지지 않게 하기 위해서다.
- 화면 안내: 해설 위에 "AI 작성" 안내(사람이 검토하지 않음, 공개 자료 근거, 숫자는 코드)를 둔다. 이번 주 TOP 10 표의 한 줄에도 AI 표시를 붙인다(D16).
- 예산: 실행당 $3 안에서 블로그 초안 다음 순서로 쓴다. 장당 약 $0.06으로 추정한다(Sonnet 5.5 — star-trend 실측 입력 1만~1.5만·출력 약 3,600토큰 기준, M7에서 다시 잰다). 주 25장이면 약 $1.5.

### F11. 글 그림 — 분석 차트와 저장소 그림 (D18~D20, 2026-11-14 추가)

블로그 초안(F7 TOP 10 글 · F9 관점 노트)과 Notion 페이지에 그림을 넣어 읽기 쉽게 한다. 사용자 요청: 다양한 분석 그림, 특이한 저장소의 그림 소개, 트렌드 분석, TOP 10 12주 비교 차트.

**차트 4종 (D18) — 코드가 계산한 숫자로 그린다, LLM 0**

| ID | 차트 | 내용 |
|---|---|---|
| C1 | TOP 10 12주 추이 비교 | 이번 주 TOP 10 의 12주 종합 순위를 선으로 겹친다(위가 1위). 후보 밖 주는 끊고, 소급 주는 옅게 |
| C2 | 신호 기여 막대 | 이번 주 TOP 10 의 신호별 기여분 쌓은 막대(합 = 지수), 빠진 신호 표시 |
| C3 | 신호 지도 | 후보 전체 — 가로 관심(스타·언급 백분위 평균) × 세로 실사용(사용·기여 백분위 평균, 사용이 없으면 기여). TOP 10 과 관점 A~D 저장소 이름, 사분면 이름 |
| C4 | 12주 트렌드 분석 | 주별 TOP 10 기여분의 신호 비중(관심형 ↔ 사용형)과 TOP 10 카테고리 분포의 12주 변화 |

- 글에 "트렌드 분석" 소제목을 둔다 — C4 와 코드 관찰 문장 + LLM 해설 한 문단(숫자는 F8 게이트).

**저장소 그림 (D19) — 관점 노트 저장소, 둘 다**

- R1 코드가 그리는 저장소 카드 — 이름·카테고리·관점 유형, 다섯 신호 백분위 막대, 12주 순위 미니 추이, 저장소 해설(F10) 3줄 요약(해설이 없으면 코드 관찰 2개).
- R2 생성 AI 일러스트 프롬프트 — LLM 이 초안과 함께 **기술 도해** 프롬프트(D24 다크 블루프린트 · 영어 장면 묘사 + 나중에 얹을 한글 라벨)를 쓴다. 사람이 이미지 AI 로 만들어 `gen/<저장소>.png` 로 두면 초안·Notion 에 결합한다(star-trend 결정 60·62 방식). 없으면 프롬프트 칸만 남는다.

**저장소 설명 그림 (D21~D23, 2026-11-14 추가) — 해설 대상 저장소(TOP 10 + 관점)**

- 저장소마다 "무엇인지 보여 주는 그림" 하나를 고른다. 순서(앞에 있는 것이 이긴다):
  1. 사람이 만든 일러스트 `gen/<저장소>.png` (R2 프롬프트로 만든 것)
  2. README 안 그림(구조도·스크린샷) — 라이선스가 허용형(MIT·Apache-2.0·BSD·ISC 등)일 때만. 배지·작은 아이콘은 뺀다
  3. 주인이 직접 올린 깃허브 소셜 미리보기
  4. 프로젝트 홈페이지의 대표 이미지(og:image)
  5. 웹 이미지 검색(Tavily 이미지 결과) — 출처 페이지를 함께 남긴다
  6. 없으면 **구조도 자동 생성** — 해설 LLM 이 README 로 "어떻게 동작하나"를 상자 3~6개·화살표로 정하고 코드가 그린다(글자는 F8 게이트)
- 그림마다 **출처와 저작권 상태**를 남긴다: 공개용(소셜 미리보기·og:image) · 라이선스(README) · 확인 필요(웹 검색) · 자동 생성(구조도). 초안·Notion 의 그림 아래에 출처를 적고, "확인 필요"는 게시 전에 사람이 본다(블로그는 사람이 검토 뒤 게시 — §2).
- 받은 그림은 이미지인지 확인하고(형식·크기 5MB 이하·폭 200px 이상, SVG 는 뺀다) 비공개 저장소 `weeks/<주>/blog/images/` 에 둔다.
- 넣는 곳(D23): 관점 저장소 카드(R1) 와 TOP 10 글의 저장소 소개.

**형식·보관**

- PNG(네이버 블로그 업로드용), 폭 1600px, 사이트 색 체계(DESIGN §3)·한글 글꼴. 비공개 저장소 `weeks/<주>/blog/charts/` 에 둔다(초안과 같은 곳, D7).
- Notion 은 파일 업로드 API 로 올려 이미지 블록으로 넣는다(star-trend 결정 62 방식). 같은 파일은 콘텐츠 해시로 다시 올리지 않는다.
- 그리기는 matplotlib(D20) — `radar/publish/charts.py` 에서만 import 한다(층 규칙으로 막는다). 글꼴은 Actions 에서 Noto Sans CJK KR, 맥에서는 시스템 한글 글꼴.

## 6. 비기능 요구사항

| ID | 요구사항 |
|---|---|
| N1 | Python 3.12+(CI 3.12), 웹은 Next.js. 표준 라이브러리 우선, 새 패키지는 사용자 확인 뒤 |

Notion에는 레이더용 데이터베이스를 새로 만들어 같은 연결에 공유한다. 웹 검색(F10)은 star-trend Tavily 키를 재사용한다(키체인·Actions Secrets `STARTREND_TAVILY_API_KEY`). 사이트 빌드용 비공개 저장소 읽기 토큰은 Vercel 환경 변수(`RADAR_PRIVATE_REPO`·`RADAR_PRIVATE_READ_TOKEN`)에만 둔다(D13) |
| N5 | Actions 권한은 최소로, 외부 Action은 커밋 SHA로 고정, 패키지는 해시로 고정한다 |
| N6 | 외부 데이터의 라이선스·출처 표기를 지킨다(ecosyste.ms CC-BY-SA, GeekNews 약관) |
| N7 | LLM은 **Sonnet 5.5(`claude-sonnet-5-5`), 실행당 상한 $3**(D4). 키를 star-trend와 같이 쓰므로 비용은 실행 기록(사용 토큰·금액)으로 따로 집계한다. 넘으면 LLM 단계만 멈추고 비용 0인 결과는 낸다. 저장소 해설(F10)도 같은 상한 안에서 블로그 초안 다음 순서로 쓴다 |
| N8 | 배포·크론 활성화 전에 워크스페이스의 보안 점검 4단계를 거친다 |
| N9 | 리포 파일명은 영어 ASCII만 |

## 7. 데이터 모델 (초안)

| 이름 | 내용 |
|---|---|
| `candidates/<주>.json` | 그 주 후보 저장소와 선정 이유 |
| `signals/<주>.csv` | 저장소 × 신호(S1~S5) 주간 값, 출처 상태, 소급 여부 |

**공개 저장소 + 글은 비공개 저장소**(D7). 코드·신호 값·지수·사이트 공개 데이터는 공개 저장소에 둔다. LLM 해설·블로그 초안·Notion 대응표는 비공개 저장소에만 두고, 크기 가드가 공개 저장소에 들어오는 것을 막는다. 저장소 해설은 사이트가 빌드 때 비공개 저장소에서 받아 화면에만 보인다(D13).
